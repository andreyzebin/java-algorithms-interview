# JIT, компиляция и прогрев JVM

## Как JVM исполняет байткод
1. **Interpreter** — читает байткод и исполняет сразу. Старт мгновенный, исполнение медленное (~в 10-50× медленнее нативного).
2. **JIT (Just-In-Time)** — горячие участки компилируются в нативный код во время работы. Быстро, но требует прогрева.

JVM по умолчанию использует **оба** (mixed mode): начинает в интерпретаторе, горячее компилит.

## Уровни компиляции (Tiered Compilation, default)
```
Level 0: Interpreter
Level 1: C1 без профилирования      (простой нативный код, для тривиальных методов)
Level 2: C1 с базовыми счётчиками
Level 3: C1 с полным профилированием (собирает данные: какие ветки, типы, частоты)
Level 4: C2                          (агрессивные оптимизации на основе профиля L3)
```
Типичный путь горячего метода: `0 → 3 → 4`.
- **C1 (client)** — быстро компилит, лёгкие оптимизации. Цель: быстрее уйти от интерпретатора.
- **C2 (server)** — долго компилит, максимум оптимизаций. Цель: пиковая производительность.

### Что делает C2 (главные оптимизации)
- **Inlining** — подставляет тело метода в вызывающий (убирает оверхед вызова, открывает другие оптимизации)
- **Escape analysis** — если объект не "убегает" из метода → аллокация на стеке / скаляризация (нет давления на GC)
- **Loop unrolling**, **vectorization** (SIMD)
- **Dead code elimination**, **constant folding**
- **Devirtualization** — монорфные вызовы по профилю → прямой вызов + inline
- **Branch prediction** по профилю L3

## Когда срабатывает компиляция
- Счётчики: вызовы метода + итерации циклов. Порог ≈ 10000 (`-XX:CompileThreshold`, при tiered сложнее).
- **OSR (On-Stack Replacement)** — длинный цикл компилируется и **подменяется прямо во время выполнения**, не дожидаясь следующего вызова метода. Видно в `-XX:+PrintCompilation` как `% `.
- **Deoptimization** — JIT откатывается в интерпретатор, если допущение нарушилось (например, подгрузился класс, сделавший devirtualization невалидной; сработала редкая ветка). Видно как `made not entrant`.

## Когда JVM работает БЕЗ JIT
- **`-Xint`** — только интерпретатор (отладка, воспроизведение багов; очень медленно).
- **`-XX:TieredStopAtLevel=1`** — только C1, без C2. Быстрый старт, нет дорогих компиляций — для короткоживущих процессов / CLI.
- **Code Cache переполнен** (`-XX:ReservedCodeCacheSize`) — JIT отключается, лог `CodeCache is full. Compiler has been disabled.` → всё уезжает в интерпретатор, деградация. Мониторить!
- **GraalVM Native Image** — нет JVM вообще, всё скомпилировано AOT (см. ниже), JIT отсутствует by design.
- Первые тысячи вызовов любого метода — интерпретатор, пока счётчики не дозреют (это и есть прогрев).

## Проблема прогрева (warmup)
Сразу после старта код медленный: интерпретатор + ещё не скомпилированные горячие методы. Пик достигается через секунды-минуты под нагрузкой.

**Почему это боль:**
- Serverless / autoscaling — новый инстанс холодный, первые запросы медленные → latency spikes
- После деплоя / рестарта — пул свежих pod'ов тормозит
- Канареечные релизы — холодный канареечный инстанс выглядит "хуже"

### Решения

| Подход | Что делает | Минусы |
|---|---|---|
| **Warmup-трафик** | гонять синтетическую нагрузку до выхода в LB | надо реалистично воспроизвести горячие пути |
| **Tiered (default)** | C1 быстро даёт приличный код, пока зреет C2 | уже включено |
| **AppCDS** (`-XX:+AutoCreateSharedArchive`) | шарит метаданные классов между запусками, быстрее загрузка классов | не ускоряет сам JIT |
| **GraalVM Native Image** | AOT-компиляция, старт <100ms, нет прогрева | нет JIT-пиковых оптимизаций, длинный билд, reflection hints |
| **Project Leyden** (новое) | AOT + кэш профилей/кода, "сдвигает" работу JVM на build-time | в развитии |
| **Azul Zing ReadyNow / OpenJDK CRaC** | сохранить профиль JIT / целиком снимок прогретой JVM и восстановить | нужен особый рантайм; CRaC требует подготовки (закрыть сокеты/файлы) |
| **C1-only для короткоживущих** | `-XX:TieredStopAtLevel=1` | нет пиковой производительности |

### CRaC (Coordinated Restore at Checkpoint) — современный приём
Снимок (checkpoint) уже прогретого процесса → восстановление за десятки мс с сохранением скомпилированного кода и профиля. Spring Boot 3.2+ поддерживает. Идеально для serverless: прогрел один раз → клонируй снимок.

### Native vs JIT — компромисс
- **Native** выигрывает старт и память, проигрывает пиковый throughput (нет адаптивных оптимизаций по реальному профилю)
- **JIT** проигрывает старт, но на долгоживущем сервисе обгоняет native через минуту
- Для долгоживущего бэкенда с прогревом — **JIT обычно быстрее в пике**; для Lambda/CLI — **native/CRaC**

## Полезные флаги / диагностика
```bash
-XX:+PrintCompilation                 # лог что и когда компилит (% = OSR, ! = exception handler)
-XX:+UnlockDiagnosticVMOptions -XX:+PrintInlining
-XX:ReservedCodeCacheSize=256m        # размер code cache
-XX:TieredStopAtLevel=1               # только C1
-Xint                                 # только интерпретатор
-Xcomp                                # компилировать всё сразу (для тестов, не для прода)
jcmd <pid> Compiler.codecache         # состояние code cache
jcmd <pid> Compiler.queue             # очередь компиляции
```
В JFR — событие "Compilation" и "Code Cache Statistics".
